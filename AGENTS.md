# Store change agreement

Preserve working project definitions, catalog offerings, capability limits, project-specific economics, and downstream records. Fix the owning layer; do not silently substitute a smaller task or rebuild working content.

Every callable pricing path must select an explicit class policy. Unknown classes remain unresolved. No generic setup/hourly/time fallback. Catalog changes are data changes through validation, not replacements with demonstration objects. A source pin or contract receipt is identity, not commercial or physical authority.

Before claiming completion, exercise the requested behavior through its actual consumer, identify exact source versions, test rejection of the targeted failure, and report any incomplete consumer coverage. Unit tests alone do not prove visible application adoption. Do not edit generated consumers by hand.

Run `node --test *.test.mjs` before proposing promotion. The Store contract and catalog/pricing behavior checks must run for every pull request. Branch protection must require the workflow before it is described as an enforced merge gate. Do not claim branch protection exists without verifying repository settings.

Do not merge, deploy, repoint consumers, or authorize physical execution without task authorization. Existing incomplete economics must remain explicit.

## Controlling dimensional Store standard

Read `STB-DIMENSIONAL-STORE-TRAVEL-STANDARD-0.1.md` before changing Store, configurator, pricing, capability, confirmation, or tests. It supersedes conflicting historical fixture rules and project-specific pricing exceptions. Do not redefine success or substitute a partial result for a complete Q. Missing facts stay explicitly unresolved.

Only Store computes current capability, modeled machine work/time, and Q. The same evaluator must run at live configuration and confirmed reconciliation. The app must preserve and check both identified results, refuse divergence, and retain the travel record. Modeled machine state never authorizes physical motion.

A material subtotal is not Q. Historical/native project economics may be retained only as identified historical reference; they cannot satisfy this standard's current complete-Q gate. No project-name pricing exemptions. Do not change tests merely to fit implementation. Report actual consumer coverage, exact tested versions, and any unimplemented clauses. Do not claim a workflow is a required merge gate unless repository protection has been verified.
